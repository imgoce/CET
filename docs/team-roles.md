# 캠퍼스 환경 펫 · 팀원별 개발 범위

기준 문서는 최종 요구사항 명세서 v1.2와 [API 계약서](./api-contract.md)다. 각 절의 RID는 엑셀에서 해당 팀원이 주 담당인 기능의 번호다. 완료 기준은 해당 RID 행의 ‘검증 기준’과 연결된 비기능 요구사항(NF)을 따른다.

## 작업을 가져가는 방법

1. 담당자는 시작할 기능을 GitHub 이슈 하나로 묶고, 제목에 RID와 기능명을 쓴다. 같은 RID의 진행 중인 이슈가 있으면 그 이슈에서 협업한다. 작은 기능은 한 이슈에 여러 RID를 적어도 된다.
2. 이슈에 **담당자 / 직접 구현할 부분 / 호출할 다른 담당 기능 / 완료 예시**를 적는다. 예를 들어 권기찬의 첫 이슈는 `[GR-1, GR-2] 먹이 사용과 레벨업 계산`이다.
3. 브랜치를 시작하기 전에 저장소에서 같은 이름의 함수·데이터 객체를 검색한다. 연결할 상대 기능이 아직 없으면 계약서의 예시 값이나 테스트용 가짜 구현으로 내 부분을 먼저 검증한다. 운영에 사용할 구현은 아래 담당자가 한 곳에서 작성한다.
4. PR에는 관련 이슈와 실제 확인한 결과를 적는다. 공통 입력·출력을 바꿀 때는 그 값을 만드는 사람과 쓰는 사람이 한 PR에서 계약 변경을 확인한다.

**공통 코드 운영 제안** — 첫 기능에 필요한 공유 Java 데이터 클래스와 메서드 선언은 ③이 계약서에 맞춰 한 번 작성해 공통 브랜치에 올린다. 예를 들어 ①·③·⑤가 모두 쓰는 `PetState`는 같은 클래스를 참조한다. ④와 ⑤는 자신이 맡은 계산 로직을 구현한다. 아래 브랜치명과 첫 작업은 시작 예시다.

## ① 정운형 · 모바일 UI 및 BLE 수집

브랜치 예시 `feat/app-ble` · 주 담당 24개

- **직접 구현** — Android 권한·BLE 스캔, 수집 시작·중지와 재시도 대기열, 닉네임·펫·피드백 화면을 맡는다. 일반·음영 수집 진행도, 먹이 잔액, 보상 알림, 랭킹을 표시하고 먹이 주기·뽑기·장착 버튼을 연결한다.
- **연결** — BLE 광고와 RSSI·수신 시각은 ④에 넘긴다. 수집은 ③의 업로드·저장 결과를 받아 재시도 여부를 처리한다. 지도에서 ②가 넘긴 `sensorNo`를 기기에 저장·복원한다. ⑤가 정한 펫 표현을 화면에 그린다.
- **첫 작업 예시** — 수집 시작·중지와 권한 거부 화면을 구현한다. 가짜 수신 이벤트로 화면을 시험하고 운영 업로드는 호출하지 않는다.

**필수 RID** · `US-1`, `US-2`, `US-2-2`, `US-3`, `DC-1`, `DC-1-1`, `DC-2`, `DC-4`, `DC-7`, `ES-1`, `ES-4`, `ES-4-1`, `RW-7`, `GR-2-1`, `RK-2`, `FB-1`, `FB-2`, `FB-2-2`, `EX-1`, `EX-2`, `EX-3`, `EX-4`, `EX-4-1`, `EX-8`

## ② 이승찬 · 센서 지도 및 환경 개선 결과 화면

브랜치 예시 `feat/map-results` · 주 담당 8개

- **직접 구현** — 센서 마커, 음영지역 표시, 마커 상세, 지도 갱신 실패·장기 미수신 표시를 맡는다. 지점·시간대별 불편, 응답 수, 점검 후보, 자료 부족 상태를 목록·상세 화면에 표시한다.
- **연결** — ③의 지도 조회와 음영지역 조회를 호출하고, ④가 정한 최신 행·음영 목록을 표시한다. 마커를 누르면 선택한 `sensorNo`를 ①에 전달한다. 결과 화면은 ④의 `SiteSlot[]`를 사용한다. 시간대별 그래프도 같은 집계 결과를 쓴다.
- **첫 작업 예시** — 지도에 예시 마커 두 개를 표시하고 B를 눌렀을 때 B의 센서 번호가 ①에 전달되는지 확인한다.

**필수 RID** · `SM-2`, `SM-3-1`, `SM-4`, `AG-4`, `AG-5`, `EX-5`, `EX-7`

**후순위 RID** · `AG-6`

## ③ 곽예찬 · 백엔드·DB 및 API

브랜치 예시 `feat/backend-db` · 주 담당 16개

- **직접 구현** — 수업 HTTP API 1·2의 요청·응답 처리, 팀 DB 저장·조회, 닉네임 접속, 참여 UUID 연결, 재전송·동시 요청 처리를 맡는다. 앱이 호출하는 팀 DB 메서드 12개를 제공한다.
  - 닉네임 등록·접속과 사용자 상태 — `registerUser`, `loginByNickname`, `getUserState`
  - 수집·피드백 저장 — `commitCollection`, `submitFeedback`
  - 선택 지점 환경·음영지역·집계용 원자료 조회 — `getSiteEnvironment`, `getShadowSites`, `getAnalysisInputs`
  - 먹이·장식 변경과 랭킹 조회 — `feedPet`, `drawCostume`, `equipCostume`, `getRanking`
- **연결** — 저장 시점의 기록으로 ④의 유효성·기여도 판정과 ⑤의 지급·성장 규칙을 적용한다. 같은 요청이 재전송되면 기존 결과를 반환한다. 참여·잔액·장식품·지급 이력 변경은 DB에서 한 번에 확정한다.
- **첫 작업 예시** — 닉네임 등록 시 기본 펫을 저장하고, 같은 닉네임으로 다른 폰에서 접속해 동일한 사용자·펫을 읽는지 확인한다.

**필수 RID** · `US-1-1`, `US-1-2`, `US-1-3`, `US-2-1`, `SM-1`, `DC-5`, `DC-5-1`, `DC-5-2`, `DC-6`, `DC-6-1`, `RW-5`, `RW-6`, `GR-4`, `CS-4`, `FB-3`, `EX-6`

## ④ 김용민 · 데이터 전처리 및 분석

브랜치 예시 `feat/data-analysis` · 주 담당 18개

- **직접 구현** — BLE 패킷 해석, 단위 변환, 유효값·RSSI·중복 검사, 10초 구간의 기여 후보 선정, 일반·음영 할당량 달성 여부와 하위 5개 음영지역 판정을 맡는다. 현장 피드백 유효성, 환경 상태, 지점·시간대 집계와 후보 판정도 구현한다.
- **연결** — ①에 정규화한 측정값을 제공하고, ③·⑤에 인정 여부와 할당량 달성 결과를 제공한다. ⑤에 온습도 상태, ②에 최신 행·음영지역·집계 결과를 제공한다. 집계 입력은 ③의 조회 메서드로 받고, `aggregateSites`에서 `SiteSlot[]`를 계산한다.
- **첫 작업 예시** — 같은 10초 구간에 유효 센서 A가 −55 dBm, B가 −72 dBm이면 A만 기여 후보가 되는지 패킷 예시로 검증한다.

**필수 RID** · `SM-1-1`, `SM-1-2`, `SM-3`, `DC-3`, `DC-3-1`, `DC-3-2`, `DC-3-3`, `DC-3-4`, `DC-5-3`, `ES-2`, `ES-2-1`, `ES-2-2`, `FB-2-1`, `AG-1`, `AG-2`, `AG-3`, `AG-3-1`

**후순위 RID** · `AG-7`

## ⑤ 권기찬 · 캐릭터 및 보상 로직

브랜치 예시 `feat/pet-rewards` · 주 담당 18개

- **직접 구현** — 온도 상태를 펫 행동에, 습도 상태를 배경에 연결한다. 첫 수집·일반 5회·음영 5회·피드백의 지급 사유와 먹이 수량을 계산한다. 먹이 사용, 성장·진화, 코스튬 뽑기 비용·추첨·장착·해제, 랭킹 순위 계산을 맡는다.
- **연결** — ④의 참여·환경 판정과 ③이 읽은 현재 펫 상태를 입력으로 쓴다. ③에 지급 사유·수량 또는 변경 후 펫 상태를 돌려주고, ①에 표시할 행동·배경·진화 결과를 제공한다. 중복 방지에서 ⑤는 같은 참여에 붙을 지급 사유를 정의하고, ③은 참여 UUID와 사유를 함께 검사해 한 번만 저장한다.
- **첫 작업 예시** — `GR-1`, `GR-2`부터 시작한다. Lv.1·진행도 0·먹이 2개인 펫에게 한 번 먹이면 Lv.1·진행도 1·먹이 1개, 다시 먹이면 Lv.2·진행도 0·먹이 0개가 된다. 이 계산은 화면과 DB 없이도 확인할 수 있다.

**필수 RID** · `ES-3`, `ES-3-1`, `RW-1`, `RW-2`, `RW-3`, `RW-4`, `GR-1`, `GR-2`, `GR-3`, `GR-3-1`, `CS-1`, `CS-2`, `CS-2-1`, `CS-2-2`, `CS-3`, `RK-1`

**후순위 RID** · `ES-5`, `GR-5`

## 같은 기능에 여러 명이 등장할 때

| 상황 | 누가 어디까지 구현하는가 |
|---|---|
| 먹이 주기 버튼 | ①이 버튼에서 ③의 `feedPet`을 호출한다. ③이 현재 펫을 읽고 ⑤의 성장 계산을 적용해 저장한다. ①은 응답의 `pet`과 `evolved`를 표시한다. |
| 수집 보상과 재전송 | ①이 수신하고 ④가 유효 측정·기여 후보를 고른다. ③이 저장 시점에 기여·할당량을 확인하고 ⑤의 규칙으로 지급량을 계산해 함께 저장한다. 같은 요청의 재전송은 ③이 최초 결과를 반환하고 ①이 알림 중복을 막는다. |
| 환경 상태와 펫 | ④가 온도 29℃를 `HOT`으로 분류하고, ⑤가 `HOT`을 ‘땀 흘리기’에 연결한다. ①이 현재 성장 단계에 해당하는 캐릭터에 그 행동을 표시한다. |
| 현장 피드백 | ①이 응답을 입력받고 ③의 `submitFeedback`을 호출한다. ④가 연결 수집·제출 시각·한도를 검증하고, ⑤가 유효한 피드백의 보상을 계산한다. ③이 피드백·횟수·지급을 한 번에 저장한다. |
| 지도와 점검 후보 | ③이 조회하고 ④가 음영 순위와 점검 후보를 계산한다. ②는 결과를 지도와 목록에 표시한다. 지도 선택은 ②가 번호를 넘기고 ①이 펫 화면용으로 저장·복원한다. |

## 코딩 도구에 붙여 넣을 문장

> 나는 [번호·이름]이고 이번 이슈는 [RID·작업명]이다. docs/team-roles.md에서 내 담당 범위와 연결 상대를 확인하고, docs/api-contract.md에서 해당 입출력을 확인해 줘. 먼저 저장소에 이미 있는 관련 클래스와 메서드를 찾아 재사용하고 이번 이슈에 해당하는 부분만 구현해 줘. 다른 팀원 기능이 필요하면 공통 인터페이스를 호출하고, 아직 준비되지 않은 구현은 테스트에서만 예시 값으로 대체해 줘. 마지막에는 관련 요구사항의 검증 기준으로 확인한 결과와 다른 팀원에게 연결해야 할 부분을 알려줘.
